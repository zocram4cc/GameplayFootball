# PES 2021 — how match body animations are chosen and played

Scope: read-only RE of the PES 2021 executable image (raw dump `<scratch>/pesmem.bin`, base 0x140000000; function bounds from the in-memory `.pdata`) and of the live process (reads of `/proc/<pid>/mem` only). VFS data came from `pesfmt_dump cat`. All scratch, scripts and outputs are in `<scratch>/AnimSelectRE/`. No PES table is reproduced here; every table below is described by its layout and can be regenerated by `decode_tables.py`.

Tags: **OBS** = observed, followed by how. **INF** = inferred, followed by a confidence.

Addresses are image VAs. `FUN_x` names are Ghidra auto-names from a headless decompile of a private, analysis-free copy of the shared project (`dec.sh`, which wraps `DecompAt.java`). Decompiles are in `out/*.txt`.

## 0. Headline facts

1. **Clip identity is a 13-bit `motionNo` in 0..4388, not a hash.**
   - OBS: the exe holds a sorted `char*` table of the 4,389 clip names at **0x14351e590** (motionNo → name).
   - OBS: debug `printf`s index it as `*(name_table + m*8)` (`FUN_1406f0f70`, `FUN_1406f0aa0`, `FUN_14072f670`).
   - OBS: the clip lives in **`body_anime_file<motionNo / 439>.mtar`**. This holds for 4389/4389 (each name's StrCode32 matched against the mtar entry hashes).
   - Inside an mtar the entries are sorted by the mtar `index` field, which is **not** the motionNo.
   - Every data table refers to clips by motionNo, usually stored as `motionNo+1` with 0 meaning "none".
2. **Gameplay gani frames are 1/30 s, not 1/59.94 s.**
   - OBS: `FUN_1406af720` returns `blendStart / 30.0f`. The constant at 0x142591140 = 30.0 (read from the image).
   - OBS: `FUN_1406b10d0`/`FUN_1406b11e0` convert a hit frame to ticks as `ticks = (2·f / playbackSpeed) · (Hz/60) + 0.5`, which is f/30 s.
   - OBS live: parametric run-loop members are started at `startTime = (frames/30) × startRate` **exactly** (§5.2).
   - INF (high, two independent reasons): a 13-frame `run_5_5` cycle at 30 fps is 0.43 s for two steps, i.e. sprint cadence. At 59.94 fps the same cycle would be 9 steps/s, which no human can do.
   - Impact on GodotFootball: `src/rig/clip_pose.hpp: PES_FRAME_S = 1/59.94` plays every match clip at 2× speed.
3. **Root raw units → metres is 1/16384, not 1/20480.**
   - OBS: `anim_infos.json` (the developer export of the Mbinfo bins, in cm) reports `root_pos_blend_*`. The gani RIG_ROOT raw displacement at the same frame divides by it to **163.72–163.82 raw/cm** on all 5 clips tested. That is 16384 raw per metre, i.e. 2^14.
   - OBS live: a player in pure `run_3_3` parametric (rate 0.5, playbackSpeed 0.998) moved at 3.88 m/s over 4.5 s. Predicted: 3.94 m/s at 1/16384 versus 3.16 m/s at 1/20480.
   - INF (medium-high): GF's calibrated 1/20480 (`PES_POS_TO_M_GAMEPLAY`) is 25 % short.
4. **Match logic tick = 54 Hz.**
   - OBS: `FUN_141e532f0` stores 54.0f into 0x14351ae54 and 54 into 0x14351ae50.
   - OBS: the same value was read live and in the dump. `FUN_141e532d0` returns it, and every frame↔tick conversion uses it.
5. **Selection is table-driven.** An action class computes a **row** (3,045 named situations) of `Animetable.bin`. A relative angle picks one of **18 columns** (22.5° buckets with ±0 split). The cell gives `motionNo + mirror`.
   - Locomotion uses its own decimal-keyed state graph (`Freemove.bin`) plus **parametric speed blends** (`Parametricblendtable.bin`).
   - Headers use per-height tables (`Idletable`/`Movetable`, keyed by `_yN`).
6. **Playback = crossfade with explicit duration in seconds**, mostly 0.133 / 0.167 / 0.2 / 0.3 s, plus a per-player playback speed of about 0.9–1.15.
   - Loop entries are phase-matched: parametric members share one normalised phase (`startRate` ∈ {0, 0.25, 0.75} observed). Single clips get a non-zero `startTime`.
   - Root motion is applied by `And::AnimMovePlugin` to the model transform, scaled per player by about 0.97–1.08.
7. **Clip names are never built at runtime** (no format string makes them). Their tokens have fixed meanings, decoded statistically from the data in §6:
   - `<family>_<speedIn>_<speedOut>_…`: speed classes 0..5;
   - `_yN`: ball-contact height class;
   - `_NNN` / `_fNNN`: ±turn in degrees.

8. **Hand poses are a per-body-clip keyframe timeline, one per hand (§11).**
   - `FHSequence/bin/Handlbase.bin` and `Handrbase.bin` give every body motionNo (key = `motionNo + 216`) a list of timed events `{handClip, startFrame, endFrame}`.
   - Hand clips are 162 single-frame finger poses on a left-hand rig.
   - The left and right hands have separate tables and separate engine controls.
   - Evaluation: hold the event's pose inside `[start, end]`, linear crossfade across gaps, at most 4 weighted poses at once. A mirrored body clip swaps the two tables.
   - Clips without a sequence fall back to 8 idle categories.
   - OBS live: hand states read for 19 characters.

- **Live states seen.**

### 2.1 Common record conventions (OBS, verified against `anim_infos.json`)

- Most Mbinfo records start with a u32 whose bits 0–12 are the **motionNo** and bits 13–20 are a **frame**.
  - CancelData: `cancel_frame`, matches the json.
  - HitData: `hit_frame`.
  - FootType: the json `frame`.
  - Further bit-fields differ per file.
- Frames are gani frames at 30 Hz.
- `anim_infos.json` (15.7 MB, dt13) is the developer-side **decoded export of all Mbinfo files**, keyed by a 4-digit developer id, not by motionNo. It has 4,907 entries; 4,105 match a body clip by name. Its field list doubles as a field glossary:
  - `start_frame`, `end_frame`, `blend_start`;
  - `root_pos_first_{x,y,z}`, `root_pos_blend_{x,y,z}`;
  - `end_move_angle`, `cancel_speed`, `emotional_value`;
  - `is_on_memory`, `has_derivations`, `is_on_animtable` (always false);
  - per-event lists: `hit_data`, `sub_hit_data`, `hold_data`, `jump_data`, `cancel_data`, `rot_data`, `demo_connect_data`, `personalized_data`, `foot_type`, `danger_data`, `pivot_info`, `pivothit_info`, `ball_data`, `move_adjust_info`, `divert_info`, `joint_pos_info`, `equal_parts_pos_info`, `camera_pickup_info`.
  - It is the **authoritative per-clip metadata to read at runtime** instead of re-decoding every bin. INF (high): the game itself uses the bins; the json is a faithful decode, checked on 6 bins.

### 2.2 `Animation.bin`: per-clip timing (OBS)

36-byte records, 4,345 of them. 44 motions have no record; the loader falls back to a default at 0x1436f2430.

| Field | Meaning | How checked |
|---|---|---|
| u32 a, bits 0–12 | motionNo | 3,315/3,321 float-matched records agree with the name table |
| u32 a, bits 13+ | `end_frame − 1` | equals the gani `frame_count − 1` |
| u32 b, bits 10–19 | `blend_start` (frame where the outgoing blend may begin; typically `end − 10…16`) | `FUN_1406af720` returns it /30 |
| u32 b, bits 0–9 | angle-like value: 0x168 = 360 in 85 % of records, the rest 270/315/405/450… | unresolved |
| f32 × 7 | `root_pos_blend_z`, `root_pos_blend_x`, `root_pos_blend_y`, `root_pos_first_x`, `root_pos_first_z`, `cancel_speed`, `end_move_angle` | matched the json |

The runtime per-motion object is 0x390 bytes, one per motionNo (`FUN_1406afbc0`):
- `+0` loaded flag;
- `+3+i` record count from Mbinfo file `i`;
- `+0x18` → Animation record;
- `+0x90 + 8k` → k-th HitData record.

### 2.3 `Animetable.bin`: the situation × angle selection table (OBS)

- **Layout.** 3045 × 18 little-endian u32 (219,240 B). Each cell: bits 0–12 = `motionNo + 1` (0 = empty), bit 13 = **mirror** (`FUN_1406aa440` parser).
- **Runtime copy.** `u16 motion[3045][18]` plus `u8 mirror[3045][18]` at +0x1ac34.
- **Row labels.** At **0x1434997f0** (3045 `char*`), used by the `[trap_check] ANIMETABLE : %s` debug print at 0x1407a11e4.
  - Labels name the situation: `dribble_0_3_out_r`, `riseup_faceup_0_3`, `kick_mid_0_0_inside_y0_f`, `wall_jump_high`, …
  - Prefix counts: demo 367, kick 278, dribble 170, trap 150, trapside 148, trapchase 126, run 105, side 77, fk 74, …
- **Lookup.** `FUN_1406abb30(tbl, &row, &col, defaultNeg1)`:
  - returns `motion[row][col]`, or −1 if empty or out of range;
  - one hard-coded patch: row 1989, col 2 → motionNo 2484, mirror forced 0.
  - `FUN_1406abd60` returns the mirror bit.
  - `FUN_1406abdd0` tests whether a column is populated.
- **Column = relative angle.** `FUN_1406de990(row, angleDeg)`:
  - for c in 0..17 with populated cells: `k = c<9 ? c : c−1`; `centre = k·22.5 − 180`;
  - if `centre == 0`: c=8 uses −0.001 and c=9 uses +0.001 (so 0° is split into a left and a right column);
  - picks the column whose centre is nearest `|angle − centre|`; default 9.
- **Result.** Columns are −180, −157.5, …, −22.5, −0, +0, +22.5, …, +180.
  - OBS: right-side rows hold clips named `…_f135/_f090/_f045` in the negative columns and `…_045/_090/_135` in the positive ones. Left-side `_l` rows hold the same clips with the mirror bit set.

### 2.4 `Kickinfo.bin` / `Idletable.bin` / `Movetable.bin`: "superior kick" tables (OBS, partial)

- **Parser.** One `ParsedJsonSuperiorKickTable` class, sub-type stored at +0x98: 0 = Kickinfo, 1 = Idletable, 2 = Movetable (`FUN_1406aa590`).
- **Idletable / Movetable.** 151 records × 20 B. Each record unpacks into about 10 (Idle) or 9 (Move) 12-bit **Animetable row** indices (stored +1) plus 1-bit flags.
  - The slots are the **ball-height classes y0..y9**.
  - OBS: e.g. record 1 = header rows `head_0_0_y5_f`, `…y6_f`, `…y7_f`, `…y9_f` (Idle = standing) versus `head_3_0_y*` (Move = running in).
- **Kickinfo.** 0x20ec/0x20 records of 7-bit fields (one stored −60, i.e. a signed angle) + 2 floats. Semantics not decoded.

### 2.5 `Freemove.bin` / `FreemoveOption.bin`: locomotion state graph (OBS layout, INF semantics)

- **Freemove layout** (parser `FUN_1406ab4c0`). 3,874 × 12 B:
  - `w1 & 0x7fffff` + 200 = **decimal key**;
  - `w2 & 0xfff` + 0x22 = **motionNo**;
  - `w0` bit 23 = mirror;
  - `w0 & 0x7fffff` = **next key**.
- **FreemoveOption layout** (parser `FUN_1406ab310`). 105 × 8 B:
  - key = `(w0 & 0x3ffffff) + 0x900b1`;
  - value = `(w1 & 0xfff) + 0x1f`;
  - mirror = bit 26.
  - Not decoded further.
- **Key = `state·10 + angleDigit`**, 408 distinct states (`freemove_decoded.txt`).
  - `angleDigit` 0..4 = turn 0/45/90/135/180°.
  - 5..9 = the same turns to the negative side. These are served by mirrored clips or by `_fNNN` clips (e.g. digit 7 → `side_2_2_run_f090`).
  - OBS: in every state the digit order matches the clip's angle token.
- **The "next key" is the code of the clip just chosen.** OBS: e.g. `idle_0_2_run_045` → 10211, `run_2_2` → 210210. The clip's own digits read, INF medium-high: `[bodyOrientation][speedIn][?][style][speedOut][?][angle]`, with leading zeros dropped.
  - Examples: `walk_1_0` = 110010, `walk_1_3_run` = 110310 (in 1, out 3), `run_3_2_side_135` = 313213.
  - `side_2_2_run_f090` = 3210217 (orientation digit 3 = side-on, angle 7 = −90).
  - `side_2_2_parallel_135` = 3212213 (style digit 2 = parallel).
- So locomotion is a finite-state machine: (current clip code, requested relative turn) → next clip. Exact meaning of the digits 2 and 5 is open.

### 2.6 `Parametricblendtable.bin`: 1-D blend spaces (OBS)

- **Layout** (parser `FUN_1406b2950`). 449 × 8 B: u32 bits 0–11 = `motionNo − 0x520`, bits 12–18 = **group** (95 groups), bit 19 = mirror; f32 = **parameter**.
- **Groups 0–79: goalkeeper blends over ball height.** Members `gk…_yNN`, parameter = NN/11 (y02 = 0.18, y04 = 0.36, …, y11 = 1.0).
- **Groups 80–93: locomotion over speed.** Example group 80: `walk_1_1` 0.0, `run_1_1` 0.15, `run_2_2` 0.3, `run_3_3` 0.5, `run_4_4` 0.9, `run_5_5` 1.0. The other groups replace one member each: relaxed, tired, near/guard, `parallel_*` sidestep, `heisou` (side-run).
- **Group 94: throw-in turn loop** (parameter 0 / 0.5 / 1).

### 2.7 Not decoded

`SlideDribble.bin` (697 KB, `ParsedJsonSlideDribbleTable`, runtime 0x186dfc B), `FHSequence/*` (face/hand sequences), `EyesTarget`, `playerID/Definedatatable` + `Derivationdatatable` (`has_derivations`: 19 clips with per-player variants), `PersonalizedData`.

## 4. From request to clip

### 4.1 The action layer

- `AnimePlayer::Exec` (`FUN_1406e5fc0`) runs the current action's virtual `Exec` (ActionManager slot chosen by `+0xac8`), then flushes any pending request into the engine:
  - `+0x375c == 1` → `BodyAnimControl::SetMotion` (`FUN_141af61c0`) + `SetSpeed` (`FUN_141af6e40`);
  - `== 2` → `SetParametric` (`FUN_141af52b0`).
- **Action kind = index into the string table at 0x1426523e0**: `ANIME_NOTHING` 0, `IDLE_RESET` 1, `MOVE` 2, `STEP_MOVE` 3, `DRIBBLE` 4, `DRIBBLE_SIDE_BACK` 5, `DRIBBLE_STEP_MOVE` 6, `TRAP` 7, `LONG_PASS` 8, `SHORT_PASS` 9, `SHOOT` 10, `SLIDING` 11, `SLIDING_KEEP` 12, `TACKLE` 13, `BLOCK` 14, `DIVE` 15, `STAGGER` 16, `FALL_DOWN` 17, `FEINT` 18, … `JOSTLE` 72, … `LINESMAN` 90, `LINESMAN_MOVE` 91, … `ANIME_DATA_DRIVEN`.
  - OBS live: linesmen = 91 while side-stepping; open-play outfielders 2/3; a trapping player 7.

### 4.2 Speed and height classes (OBS constants)

- **Speed class.** `FUN_1406deb30` buckets km/h against `{2.5, 8.0, 13.5, 22.0}` (live table at 0x14344e250): 0 = still, 1 = walk, 2 = jog, 3 = run, 4 = dash.
  - Speed is computed as `metres_per_tick · 54 · 3600 / 1000` (`FUN_14072f670`).
  - Class 5 exists only as `run_5_5`, the top of the speed blend.
- **Ball height class.** `yN` = contact height in about 22.5 cm steps. OBS: `hit_data.ball_pos_y` (cm) per `_yN` token over all json clips:

  | Class | Contact height (cm) |
  |---|---|
  | y0 | 11–20 (ball on the ground, radius 11 cm) |
  | y1 | 20–44 |
  | y2 | 46–66 |
  | y3 | 64–89 |
  | y4 | 88–120 |
  | y5 | 113–146 |
  | y6 | ≈146–156 |
  | y7 | 158–179 |
  | y8 | 184–194 |
  | y9 | ≈213 |

  - GK clips use y00..y11 with blend parameter = N/11.

### 4.3 Request → clip, per family

1. **Discrete actions** (kick, trap, dribble touch, rise-up, contact, tackle, …):
   - The action computes an Animetable **row** from its situation: action type, incoming/outgoing speed class, height class, foot, near/far, left/right.
     - Rows are named, e.g. `[trap_check] stateIn=%d stateOut=%d moveSpeed=%d height=%d trapType=%d hitFrame=%d`, then `ANIMETABLE: %s`.
   - It then computes a **relative angle** (target direction − body facing, wrapped to ±180°) and calls `FUN_1406de990` for the column.
   - The cell gives `motionNo` + mirror. The action then calls `AnimePlayer::SetMotion(m, startTime, mirror, playbackSpeed, duration, transitionType)`.
   - Fully traced example, OBS (`FUN_1406deed0`, rise-up after a fall):
     - lying state from `DemoConnectData` (2 allfours / 3 facedown / 4 faceup) → row `riseup_<state>_0_0` (stays put) if the next target is within 1.5 m, else `riseup_<state>_0_3` (gets up into a run);
     - column from the angle to the target;
     - then `AdjustTransXZ` toward the target over `round(Hz·6/60)` ticks with factor 0.9;
     - then `SetMotion(m, 0, mirror, …)`.
   - Same pattern, OBS, in `FUN_14072f670` (jump/keeper contact): speed classes 0/1/2 at 8 and 22 km/h; duration from `FUN_14072d0b0`, or 0.2 s for kind 0x11.
2. **Headers.** Superior-kick tables (§2.4) map height class → Animetable row; idle versus moving approach uses separate tables.
3. **Locomotion (run at speed v, turn angle θ).**
   - Steady running is a **parametric blend** (§2.6, §5.2) with blend rate ≈ normalised speed.
     - OBS live: rate 0 ↔ 1.4 m/s; ≈ 0.3 ↔ 3.1 m/s; 0.5 ↔ 3.9–4.6 m/s; ≈ 0.8 ↔ 6.5–7.7 m/s.
     - These match linear interpolation of the members' natural root speeds at 30 fps: walk 1.36, run_1 1.15, run_2 3.08, run_3 3.95, run_4 7.47, run_5 8.96 m/s.
   - Starts, stops, turns and side or back steps are single clips picked by the **Freemove** state graph from the current clip code + turn bucket (0/45/90/135/180°, ±).

### 5.2 Parametric blends and phase sync (OBS)

- **Call.** `SetParametricBlendMotion(group, startRate, mirror, ?, duration, blendRate, transitionType)` (`FUN_1406f14e0`; format string at 0x1425de700).
- **Members.** For each group member it pushes `{motionNo, startTime = clipLength(m) · startRate, mirror}`, where `clipLength = blend_start/30` (`FUN_1406af720`), and the member's parameter point.
- **Live, decisive.** Group 80 at startRate 0.75 gave member start times walk 0.900, run_1 0.500, run_2 0.550, run_3 0.525, run_4 0.350, run_5 0.325 s. That is exactly `frames/30 × 0.75` for the members' 36/20/22/21/14/13 frames.
  - startRate values seen: 0.0, 0.25, 0.75.
- **Phase sync.** All blended loops run at one **normalised phase**: their foot cycles are aligned by construction.
  - INF (medium-high): the quarter steps 0 / 0.25 / 0.75 are the foot-phase markers (§5.3).
- **Blend rate.** Stored at +0x3bb4. Values seen 0.000–0.852, roughly ground speed normalised to the `run_5_5` speed.
  - OBS: rate 0.5 held 4.5 s at 3.88 m/s.
  - INF: the engine interpolates linearly between the two bracketing parameter points; the interpolation code was not read.

### 5.3 Foot phase

- **`FootType.bin` / json `foot_type`.** A per-clip list of `(frame, type 0..3)` events.
- **Types.** OBS: foot heights from GF `fk_pose` on `run_3_3` (frames 0/6/10/16/21 → 0/1/2/3/0) show:
  - type 0 = left foot planted, right swing apex;
  - type 1 = right foot strike;
  - type 2 = right planted, left apex;
  - type 3 = left foot strike.
  - INF (high) from that pattern, repeated on walk and run clips.
- **Cycle.** Loop clips start and end on type 0. The 4 events sit at about 0, ¼, ½, ¾ of the cycle, which matches the startRate quantisation.
- **Single-clip start times.** Live `startTime`s of single (non-parametric) clips are multiples of **1/54 s** (0.019 = 1 tick, 0.111, 0.148, 0.185, 0.259, 0.278, 0.426, 0.593, 0.611, 0.722, 0.815, 0.926). So the phase offset is computed in logic ticks.
  - Tried: inverting `ticks = int(1.8·frame + 0.5)` and matching to `foot_type` frames. Only partial agreement. The exact formula is **open**.
- **Engine plugin.** `And::AnimSyncPlugin` (2 per character) runs a sync step (`FUN_141b11420`):
  - copies a phase from the leading layer;
  - mode 1 sets the layer weight to a stored value;
  - mode 2 sets `(1 − w)·k`.
  - INF (medium): this is the engine-side layer time/weight sync. Internals not decoded.

### 5.4 Root motion → player transform

- **Engine** (OBS, `FUN_141afd400` = `AnimMovePlugin` apply):
  - takes the model world matrix;
  - rotates the per-frame root translation delta by the model rotation, scales it by plugin +0xc0, and adds it to the translation;
  - multiplies in the root rotation delta.
  - Override switches: +0x81 lock translation to +0x90 xyz; +0x82 lock rotation to quaternion +0xa0; +0xb0 force height +0xb4; +0xb8 force yaw +0xbc.
  - OBS live (25 plugins):
    - scale values 0.9711, 1.0, 1.0279, 1.0305, 1.0502, 1.0781. INF (medium): a per-player body-size factor;
    - most have the rotation lock on;
    - two have the translation lock on.
- **Gameplay.**
  - Per tick, the game predicts the clip's landing point as `pos + R(facing)·rootOffset(m, mirror)` (behaviour vtable +0x80/+0x88, stored at +0x34e4).
  - It corrects error with **`AdjustTransXZ` / `AdjustTransY` / `AdjustAngle`**, which spread a position/angle error over N ticks (e.g. `Hz·6/60` ticks with factor 0.9 in rise-up).
  - OBS: player ground speed tracks the blended clip root speed × playbackSpeed (§4.3.3).
  - OBS: per-update displacement of a player in `mid_delayback_1_1` (`hf.py`) oscillates with the stride, about 0.017–0.021 m per 17 ms, of the same order as the clip root profile.
  - INF (medium-high): PES match movement is **animation-driven**; the root track moves the player, and gameplay steers by choosing clips, tuning playbackSpeed and the parametric rate, and applying Adjust* corrections.
  - The exact split between logic position and root motion is open (see §9).

## 6. Clip naming convention

**OBS: names are only data.** No format string builds them (searched `_%d`, `_y%`, `%03d`, `_f%`, `%s_%s`; none relates to clips). They exist as the static name table (§0.1) and the Animetable row labels.

Token meanings, from statistics over the json and the decoded tables:

- **`<family>_<a>_<b>_…`** (1,398/4,389 names follow this prefix shape). `a` = speed class entering, `b` = speed class leaving (0 = still … 4 = dash, 5 = top sprint).
  - OBS: median first-frame root speed rises 2.6 / 4.6 / 7.4 / 10.9 / 18.6 cm per frame for a = 0..4.
  - OBS: `cancel_speed` rises with b.
  - OBS: run loops `run_N_N` are the members of the speed blend.
  - Examples:
    - `idle_0_2_run_045`: from still into a jog, turning +45°;
    - `run_2_4_000`: jog → dash, straight;
    - `riseup_faceup_0_3`: get up, then run off;
    - `sliding_0_0_000`: a slide from standing, 0° (single family).
- **`_NNN` / `_fNNN`.** Turn or direction in degrees (000, 011, 022, 045, 067, 090, 122, 135, 150, 180, 225, 270, …), and `f` = the negative side.
  - OBS: median `rot_data.rot_angle` = +NNN for `_NNN` and −NNN for `_fNNN` for every bucket. E.g. `_090` → +90.0, `_f090` → −90.0, `_f045` → −45.0.
  - Positive turns move the root toward **+X** of the clip's root space, i.e. `atan2(x, z) > 0`, OBS: `root_pos_blend` median x > 0 for `_090`.
  - In the Animetable, negative columns hold `fNNN` clips and positive columns hold `NNN` clips.
- **`_yN` / `_yNN`.** Ball contact height class (§4.2 table).
- **Side and mirror.**
  - Rows ending `_l` / `_r` are the left and right situation variants. One authored side is reused mirrored (mirror bit) for the other.
  - Clip-name `_l` / `_r` / `_R` = authored side.
  - `head_…_f` / `_r` in header rows = forward / rear header (INF).
- **Families and qualifiers** (INF from the decoded tables):
  - `dm_` = demo/cutscene (`dm_tu_` time-up, `dm_goal_`, `dm_miss_`, `dm_oop_` out of play);
  - `js_` = jostle;
  - `gk…` with `f00/s01/b01`-style codes = keeper direction (front/side/back) and distance step;
  - `kick_{short,mid,long}` plus foot part `inside / instep / outside / toe / sole / heel / infront`;
  - `trap{,side,back,lift,run,through,chase,fast}`;
  - `dribble{,run,slide045/090/180}`;
  - `feint*`, `tackle{foot,shoulder,hold}`, `block*`, `stagger_*`, `fall_{up,low}body_*`, `riseup_*`;
  - movement styles `walk / run / side / back / slant / backslant / parallel / heisou (side-run) / step / backstep / delay`;
  - modifiers `relax`, `hurry`, `tired`, `guard`, `near / mid / far` (distance to the opponent or the ball), `in / out` (touch toward or away from the body), `late`, `loop`, `noloop`, `vNN` / `verNN` = variants.

- **Layer mask types 4–6** names: brute force over arm/hand/body word combinations failed.

## 10. Notes for the reimplementation

- Play match ganis at **30 fps**. Read root translation at **1/16384 m per raw unit**. Run match logic at whatever rate you like, but PES's own is 54 Hz, and its blend durations are in seconds.
- **Per-clip metadata to load at runtime:** motionNo ↔ name (exe table, or StrCode32 match against the mtar hashes plus `anim_infos.json` names), `blend_start`, `end_frame`, `foot_type`, `hit_data` (frame, bone, ball offset), `cancel_data`, `rot_data`. All of it is in `anim_infos.json`, which is plain JSON in dt13.
- **Locomotion:** a 1-D parametric blend over {walk_1_1 0, run_1_1 0.15, run_2_2 0.3, run_3_3 0.5, run_4_4 0.9, run_5_5 1.0}:
  - all members share one normalised phase;
  - enter at phase 0 / 0.25 / 0.75 matched to the foot state;
  - the rate tracks speed / sprint speed.
- **Transitions:** Freemove-style clips selected by the current-state code + turn bucket (5 buckets per side); crossfade 0.133–0.3 s.
- **Discrete actions:** Animetable row by situation + 18-column angle pick (22.5° steps, ±0 split, nearest populated column) → motionNo + mirror; crossfade mostly 0.2 s; then steer the root with an Adjust-style correction spread over about 0.1 s.

### 11.2 Sequence data: hand clip per body clip (OBS)

- **Files.** `common/anime/FHSequence/bin/{Faceadd, Facebase, Handlbase, Handrbase, Hitframes, Sequenceinfo}.bin`.
  - Loaded by `FUN_141ed75a0`, class `draw::anime::SequenceFileListLoader`, type index 0..5 in that order.
  - Parsed by `FUN_141ed48f0`.
- **Runtime table.** `0x122d` slots × 0x70 B (`FUN_141ed4680`):
  - **slot = motionNo** for 0..0x1124;
  - 0x1125..0x122c are runtime-loaded slots (`FUN_141ed7880` parses a buffer at runtime);
  - plus a 218-entry overflow table for keys below 216.
  - Slot layout: +0x00 face-add events, +0x18 face-base events, **+0x30 left-hand events**, **+0x48 right-hand events** (vectors of 0x38-byte `FHSequenceBase` objects); counts at +0x60..+0x63; +0x64 hit-frame byte; +0x66..+0x6a flags; +0x6b loaded; +0x6e u16 sequence **key**.
- **`Handlbase.bin` / `Handrbase.bin` records** (12 B, `w0`, `w1`, `w2`; 9,524 L and 9,887 R records):

  | Field | Bits | Meaning |
  |---|---|---|
  | id | `w0` 0–12 | slot = `id − 216` = **motionNo**. An id below 216 goes to the overflow table under the negative value |
  | handClip | `w1` 20–27 | hand-name-table index (stored at event +0x28) |
  | startFrame | `((w1 >> 10) & 0x3ff) − 11` | event +0x2a |
  | endFrame | `(w1 & 0x3ff) − 8` (L) / `− 9` (R) | event +0x2c |
  | clip-local start frame | L: `((w2 >> 5) & 0x1f) − 1`; R: `(w1 >> 28) − 1` | event +0x2e; nearly always 0 |
  | clip-local end frame | L: `(w0 >> 25) & 0x3f`; R: `w0 >> 25` | event +0x30; nearly always 1 |

  Frames are body-clip frames at 30 Hz.
- **Proof that slot = motionNo.** The two candidate keys were tested on hand semantics (`hatanigiri`, `kp_*`, `taore`):

  - The 12-bit field (`w0 >> 13`) gives nonsense (`taore` on `feint`/`kick`).
  - OBS live: one linesman's FH key 3171 resolves through Sequenceinfo to id 3001 → motionNo 2785 = `layer_assistant_flag_hand_R`. That is exactly the upper-body layer motion his AnimePlayer showed (`+0x27e4 = 2785`).
- **`Sequenceinfo.bin`** (8 B: `w0`, `w1`; 3,855 records):
  - `w0` 0–12 = id; 13–24 = key → slot +0x6e;
  - 25–29 → +0x6a, a 5-bit category (INF: face expression class);
  - bit 30 → +0x68 = **right hand: ignore this clip's sequence, keep the fallback**;
  - bit 31 → +0x67 = the same for the **left** hand;
  - `w1` bit 0 → +0x69, bit 1 → +0x66.

- **Statistics** (`hand_names.json`, inline decode):
  - **Typical event shape**: `endFrame − startFrame` is 1–6 frames in about 75 % of events (a short key), 30 in about 7 %.
  - Most used clips: `normal`, `normal2`, `normal_yubimage`, `move_nigiri`, `amanigiri`, `normal3`, `nigiri`, `hiraki_normal`, `taore`, `relax`, `kp_hold`.
  - Number of motions with a hand sequence: 1,848 (left) and 1,850 (right) of 4,389.

### 11.3 Selection rule (OBS, `FUN_1406f82f0` → `FUN_141eb9a30`)

Each frame `AnimePlayer` calls the face/hand updater on its FH object (`AnimePlayer+0x3ae0`) with:

- `seq` = the **upper-body layer motion** (`+0x27e4`) when one is active and certain action kinds hold; otherwise the **current body motionNo**;
- `t` = that clip's current time in seconds (`FUN_1406e6c40`);
- `mirror`;
- a **fallback category** 0..7, chosen from player state:
  - default 0;
  - 1 when within a small squared distance of a reference point, or for certain action states;
  - 2 for player ids 23–24 (the linesmen; their fallback is the flag grip);
  - 3/4/5 for `AnimePlayer+0x2790` state 4/5/6;
  - 6 for state 7;
  - 7 when a per-team value is below 1.

**Branch A: the slot is loaded** (`+0x6b`). `FUN_141ebbb20` evaluates face-add → face-base → hand L → hand R. **Mirror swaps the hands**: with `mirror` set, the left output slot is computed from the **right** table and vice versa.

**Branch B: no sequence for this motion.** The updater uses a built-in fallback set. A 17-entry `{key, category}` table at 0x142b67ef0 is resolved at init to slots via +0x6e:

| Category | Fallback hand content (L / R) |
|---|---|
| 0 | idle loops of `normal_yubimage` / `amanigiri` / `relax` (21–42 frames) |
| 1 | `relax` ↔ `normal_yubimage` loops (14–69 frames) |
| 2 | `normal2` / `hatanigiri` (linesman flag) |
| 3 | `kp_catch_before` (keeper ready) |
| 4 | `open_full_half` |
| 5 | `normal` |
| 6 | `kp_hold` (keeper holding the ball) |
| 7 | `relax` |

- Branch B timing: time accumulators advance by `1/54 s` per tick and are clamped to each fallback's last `endFrame`.
- Branch B switching: the category may change only when it differs and at least **0.2 s** (0x142598578) has passed.

### 11.4 Evaluation and blending (OBS, `FUN_141ebb160` left / `FUN_141ebb640` right)

- **Output per hand** (FH object +0xb0 left, +0xe0 right; +0x50 face add, +0x80 face base):
  - `u8 n` (≤ 4);
  - `u8 clip[4]`;
  - `f32 localTime[4]` (+8);
  - `f32 weight[4]` (+0x18);
  - `f32 t` (+0x28);
  - `u16 key` (+0x2c).
- **Engine side.** One FH object holds a face `GenAnimControl` (+0) and **two independent hand `GenAnimControl`s** (+8 left, +0x10 right), each created with **4 tracks** (`FUN_141eb6840`).
  - Defaults: all 4 hand tracks = clip 0x59 = `normal3`, weight 1.
  - OBS live: about 40–47 hand controls ≈ 2 per character; `GenAnimControl+0x100` → the shared 162-clip resource.
- **Algorithm** for body time `t` (s), with `s_i = start_i/30` and `e_i = end_i/30`:
  1. **In-window events.** Every event with `s_i ≤ t ≤ e_i` is in the output (the **last** event stays active for every `t ≥ s_last`, so the final pose holds).
     - Its clip-local time is `(t − s_i)/(e_i − s_i) · (clipEnd − clipStart)/30 + clipStart/30`, i.e. the event window is stretched over the pose clip. That is frame 0 → 1 of a 1-frame gani, effectively static.
     - Weight: the first event gets 1. Each later overlapping event k gets `w_k = clamp((t − s_k)/(e_{k−1} − s_k), 0, 1)` and the previous one gets `1 − w_k`, a linear crossfade across the overlap.
     - At most 4 events are kept.
  2. **Gap.** If no event is in its window, find consecutive events with `e_{i−1} ≤ t ≤ s_i` and output both: the previous pose at its end, the next pose at its start, with `w = clamp((t − e_{i−1})/(s_i − e_{i−1}), 0, 1)` for the next and `1 − w` for the previous. This is a **linear interpolation between consecutive key poses**.
  3. **Fallback flag.** If the call's fallback flag is set and the slot's Sequenceinfo hand bit (+0x67 left / +0x68 right) is set, or the slot is not loaded, the hand keeps evaluating the stored fallback sequence (FH +0x120/+0x12c left, +0x12e/+0x13c right).
- **Body crossfade (replay path).** In the replay path (`FUN_14217f380` → `FUN_141eb7930`, per-player recorded state), current and previous sequences are blended over **0.275 s** (0x1425e4a24): current × `τ/0.275`, previous × `(1 − τ/0.275)`, merged into the 4 slots.
  - In play (`FUN_141eb9a30`), a new body motion re-evaluates immediately; the previous state is copied to FH +0x112.. but not blended in this function.
  - INF (medium): any smoothing then comes from the engine track transition; not traced.
- **Wrist composition.** INF (medium-high):
  - the hand clip animates only the hand-rig joints (`skh_hand_l` + 19 finger joints);
  - each hand `GenAnimControl` drives the character `Model` (+0x110) through an `AnimConvertBoneSpacePlugin` (+0xf8). The body ganis carry no finger tracks (their 20 units are body bones);
  - so the finger local rotations come from the hand pose blend and the wrist (`sk_hand_*`) from the body clip;
  - the right hand reuses the left-authored pose through the R control's bone mapping/mirror. The plugin's L→R mapping was not decoded.
- **Rig note.** GodotFootball's `rig_names` already has `skh_<finger>_<seg>_<l|r>` finger nodes, so the same 19 local rotations can be applied per side, mirrored for the right.

### 11.6 Implementation recipe

1. Load the 162 hand ganis. Each is one 20-bone pose; index = upper-case-sorted name order.
2. Load `Handlbase`/`Handrbase`/`Sequenceinfo`. Per record: `motionNo = id − 216`; push `{clip, start = ((w1>>10)&0x3ff) − 11, end = (w1&0x3ff) − 8|9}` to that motion's left or right list, in file order.
3. Each frame, for the active body clip (or its upper-body layer clip) at time `t`: if mirrored, swap the lists. Evaluate each hand with the in-window / overlap-crossfade / gap-lerp rule (§11.4), at most 4 poses with weights summing to 1. If the list is empty, or the Sequenceinfo hand bit is set, use the category fallback (§11.3), looping with 0.2 s minimum dwell.
4. Blend finger local rotations by weight: nlerp of quaternions per joint is enough for 1–4 static poses. Apply to `skh_*` finger joints; mirror the left-authored pose for the right hand. Keep the wrist from the body clip.

- keys below 216 other than the fallback set (e.g. referee clips).
